# 流程管理使用指南

> 本文档面向使用流程管理功能的开发者和最终用户，介绍如何设计流程、指派审核人、以及各类审批操作的使用方法。

---

## 一、快速入门

### 1.1 什么是流程管理

流程管理基于 Warm-Flow 工作流引擎，让你可以：

- **可视化设计**审批流程（拖拽式设计器）
- **动态指派**审核人（按角色/用户/发起人）
- **灵活流转**：通过、驳回、转办、委派、加签、减签、终止、撤销

### 1.2 核心概念

| 概念 | 说明 |
|------|------|
| **流程定义** (Definition) | 流程的"模板"，定义了节点、连线、审核人规则 |
| **流程实例** (Instance) | 流程的"一次运行"，关联具体的业务数据 |
| **任务** (Task) | 某个审核人需要处理的待办事项 |
| **历史任务** (HisTask) | 已完成的审批记录，形成审批链路 |
| **节点** (Node) | 流程中的步骤，如"开始→组长审批→经理审批→结束" |
| **权限标识** (permissionFlag) | 决定"谁能处理这个节点"的标记 |

## 二、流程设计

### 2.1 打开设计器

访问流程设计器入口：

```
GET /warm-flow-ui/index?id={definitionId}&disabled={disabled}
```

- `id`：新建流程时留空，编辑已有流程时传入流程定义ID
- `disabled`：`true` 为查看模式（不可编辑），`false` 或留空为编辑模式

### 2.2 节点类型

| nodeType | 名称 | 说明 |
|:--------:|------|------|
| **0** | 开始节点 | 流程起点，自动流转，不需要人工处理 |
| **1** | 中间节点 | 审批节点，需要人工操作（通过/驳回等） |
| **2** | 结束节点 | 流程终点，到达后流程状态变为 `complete` |

### 2.3 如何指派审核人（关键！）

审核人通过节点的 **`permissionFlag`** 字段来指派。支持以下格式：

#### 2.3.1 按角色指派

```
permissionFlag: "role:1"
permissionFlag: "role:1@@role:2"        ← 多个角色，用 @@ 分隔
```

- `role:1` 表示角色ID为1的所有用户都可以处理此节点
- `role:1@@role:2` 表示角色1或角色2的用户都可以处理
- **含义**：具有任一指定角色的用户都会收到待办任务

#### 2.3.2 按用户指派

```
permissionFlag: "user:zhangsan"
permissionFlag: "user:zhangsan@@user:lisi"
```

- `user:zhangsan` 表示只有用户 zhangsan 可以处理
- 多个用户同样用 `@@` 分隔

#### 2.3.3 指定流程发起人

```
permissionFlag: "warmFlowInitiator"
```

- 特殊值，表示由流程的发起人来处理
- 常用于"重新提交"或"发起人确认"节点

#### 2.3.4 混合使用

```
permissionFlag: "role:1@@user:boss@@warmFlowInitiator"
```

- 角色1的用户、用户boss、流程发起人，任一满足即可

#### 2.3.5 设计时 vs 运行时指派

| 方式 | 时机 | 适用场景 |
|------|------|---------|
| **设计时指派** | 在流程设计器中配置节点的 `permissionFlag` | 审核人规则固定（如"部门经理"） |
| **运行时指派** | 启动流程时传 `permissionFlag` 参数 | 审核人动态变化（如"申请人所在部门的经理"） |

**运行时示例（启动流程时动态指派）：**

```json
POST /flowIns/start
{
  "flowCode": "leave_apply",
  "businessId": "BIZ-2026001",
  "permissionFlag": ["role:2", "user:zhangsan"],
  "message": "提交请假申请"
}
```

> **注意**：运行时传入的 `permissionFlag` 会**覆盖**设计时配置的 `permissionFlag`。如果设计时已配置且不需要动态改变，启动流程时可以不传。

### 2.4 配置跳转路径（skipList）

每个节点需要配置"通过后去哪"和"驳回后去哪"：

| skipType | 含义 | 连线指向 |
|----------|------|---------|
| `PASS` | 通过 | 下一个审批节点 |
| `REJECT` | 驳回 | 上一个节点或发起节点 |

**重要**：每个中间节点都应该至少配置一条 `PASS` 连线和一条 `REJECT` 连线，否则驳回操作会因找不到路径而失败。

### 2.5 一个完整的流程示例

请假申请流程：**待提交 → 组长审批 → 部门经理审批 → HR审批 → 结束**

```
开始 ──→ [待提交] ──PASS──→ [组长审批] ──PASS──→ [部门经理审批] ──PASS──→ [HR审批] ──PASS──→ 结束
              ↑                                        │
              └──────────── REJECT ────────────────────┘
```

对应的节点配置要点：

| 节点 | 审核人 | 说明 |
|------|--------|------|
| 待提交 | `warmFlowInitiator` | 发起人自己填写 |
| 组长审批 | `role:1@@role:2` | 角色1或角色2 |
| 部门经理审批 | `role:1@@role:2` | 同上 |
| HR审批 | `warmFlowInitiator` | 发起人确认（这里用发起人是举例） |

## 三、如何使用各种审批操作

### 3.1 审批通过

```
POST /flowTask/pass
```

```json
{
  "taskId": 555666777,
  "message": "同意请假",
  "variable": {},
  "permissionFlag": ["role:2"]
}
```

**操作效果**：
- 当前任务标记为"已通过"
- 流程沿着 `PASS` 连线流转到下一个节点
- 下一节点的审核人收到新的待办任务

**结合 permissionFlag 的用法**：
- 如果下一节点的审核人已在流程设计中配置，可以不传 `permissionFlag`
- 如果需要动态指定下一节点的审核人（覆盖设计时配置），传入 `permissionFlag`

### 3.2 审批驳回

```
POST /flowTask/reject
```

```json
{
  "taskId": 555666777,
  "message": "请假理由不充分，请重新填写",
  "nodeCode": "2"
}
```

**操作效果**：
- 当前任务标记为"已驳回"
- 流程沿着 `REJECT` 连线回到之前的节点
- 可选 `nodeCode` 参数跳转到指定节点（如直接驳回到发起人）

**注意**：如果流程设计中当前节点没有配置 `REJECT` 连线，驳回操作会失败。务必在设计时为每个中间节点配置驳回路径。

### 3.3 转办（Transfer）— 彻底移交

```
POST /flowTask/transfer
```

```json
{
  "taskId": 555666777,
  "message": "我不熟悉这个业务，转给李四处理",
  "addHandlers": ["user:lisi"]
}
```

**转办 vs 委派 的核心区别**：

| 维度 | 转办 (Transfer) | 委派 (Depute) |
|------|----------------|---------------|
| **处理权** | 彻底移交，原办理人**失去**处理权 | 临时授权，原办理人**保留**处理权 |
| **审批后** | 无需回退给原办理人 | 被委派人审完后**回到**原办理人 |
| **适用场景** | 换人处理（永久） | 出差/请假时让人代批（临时） |
| **我的待办** | 从原办理人待办中**消失** | 原办理人待办**保留** |

**操作效果**：
- 目标办理人（李四）收到新任务
- 原办理人的任务关闭，不再出现在待办中
- 流程仍停留在当前节点
- 历史记录标记为 `TRANSFER`

### 3.4 委派（Depute）— 临时授权

```
POST /flowTask/depute
```

```json
{
  "taskId": 555666777,
  "message": "出差中，委派王五代批",
  "addHandlers": ["user:wangwu"]
}
```

**操作效果**：
- 被委派人（王五）收到新任务
- 原办理人的任务**保留**，仍在其待办中
- 被委派人审批完成后，任务回到原办理人
- 历史记录标记为 `DEPUTE`

### 3.5 加签（AddSignature）— 增加审批人

```
POST /flowTask/addSignature
```

```json
{
  "taskId": 555666777,
  "message": "需要法务赵六也审批",
  "addHandlers": ["user:zhaoliu"]
}
```

**加签详解**：

加签是指在已有审批人的基础上，**动态增加**额外的审批人。这是流程运行中最常用的灵活操作之一。

**使用场景**：
- 审批过程中发现需要额外人员确认（如涉及法务、财务）
- 需要更高层领导把关
- 跨部门协作，需要其他部门意见

**操作效果**：
- 新增办理人（赵六）获得一个独立的待办任务
- 原办理人的任务不受影响
- **原办理人和加签人并行审批**（形成会签）

**会签规则**：
- 节点的审批策略决定何时流转：全部通过 or 任一通过
- 如果策略是"全部通过"，则原办理人 + 所有加签人都要通过后才流转
- 如果策略是"任一通过"，则任一人通过即流转

**加签后的审批流程示意**：

```
原任务(张三待办) ────┐
                     ├──→ 全部通过 → 下一节点
加签任务(赵六待办) ──┘
```

**可以加签多个人**：

```json
{
  "taskId": 555666777,
  "message": "需要法务和财务都确认",
  "addHandlers": ["user:zhaoliu", "user:qianqi"]
}
```

### 3.6 减签（ReductionSignature）— 移除审批人

```
POST /flowTask/reductionSignature
```

```json
{
  "taskId": 555666777,
  "message": "李四不需要审批了，移除",
  "reductionHandlers": ["user:lisi"]
}
```

**操作效果**：
- 指定办理人的待办任务被关闭
- 该办理人不再参与当前节点的审批
- 其他办理人的任务不受影响

**注意**：减签只能移除**加签进来**的办理人，不能移除流程设计时配置的固定办理人。

### 3.7 终止（Termination）— 强制结束

```
POST /flowTask/termination
```

**按任务终止：**
```json
{
  "taskId": 555666777,
  "message": "业务取消，终止此流程"
}
```

**按实例终止：**
```json
{
  "instanceId": 987654321,
  "message": "业务取消，终止此流程"
}
```

**操作效果**：
- 关闭该实例的**所有**待办任务
- 实例状态变为 `termination`
- **不可恢复**，需要重新发起才能走审批

### 3.8 撤销（Revoke）— 发起人撤回

```
POST /flowTask/revoke
```

```json
{
  "instanceId": 987654321,
  "message": "填写有误，撤回修改"
}
```

**撤销 vs 终止的区别**：

| 维度 | 撤销 (Revoke) | 终止 (Termination) |
|------|--------------|-------------------|
| **操作人** | 通常是发起人 | 审批人或管理员 |
| **效果** | 回到起始节点，可重新提交 | 流程彻底结束 |
| **可恢复** | 可以（重新提交） | 不可恢复 |

**操作效果**：
- 流程回到起始节点（发起人待办）
- 必须传 `instanceId`（不能传 `taskId`）
- 历史记录标记为 `REVOKE`

## 四、完整使用流程示例

### 场景：员工请假审批

#### Step 1：设计流程

在流程设计器中拖拽设计：

```
[开始] → [待提交(发起人)] → [组长审批(role:1)] → [经理审批(role:2)] → [结束]
```

为每个审批节点配置 `PASS` 和 `REJECT` 连线。

#### Step 2：发布流程

```
POST /flowDef/publish?id=123456789
```

#### Step 3：激活流程

```
POST /flowDef/active?id=123456789
```

#### Step 4：发起人提交请假申请

```
POST /flowIns/start
{
  "flowCode": "leave_apply",
  "businessId": "LEAVE-2026001",
  "message": "申请年假3天",
  "variable": { "days": 3, "reason": "家中有事" }
}
```

#### Step 5：组长查看待办

```
GET /flowTask/myTodo
```

组长在待办列表中看到此任务。

#### Step 6：组长加签（如果需要）

组长觉得需要HR确认，执行加签：

```
POST /flowTask/addSignature
{
  "taskId": 555666777,
  "message": "请HR确认该员工年假余额",
  "addHandlers": ["user:hr_zhang"]
}
```

#### Step 7：组长审批通过

```
POST /flowTask/pass
{
  "taskId": 555666777,
  "message": "同意请假"
}
```

#### Step 8：经理查看待办 → 审批通过

```
POST /flowTask/pass
{
  "taskId": 555666778,
  "message": "批准"
}
```

#### Step 9：流程完成

流程到达结束节点，状态变为 `complete`。

#### 查看审批链路

```
GET /flowTask/hisList/987654321
```

返回完整审批历史：
```
发起人提交 → 组长加签(HR) → 组长通过 → 经理通过 → 完成
```

## 五、常见问题

### 5.1 permissionFlag 的格式是怎样的？

格式为 `<类型>:<标识>`，多个值用 `@@` 分隔：

- `role:1` — 角色ID为1
- `user:zhangsan` — 用户名为 zhangsan
- `warmFlowInitiator` — 流程发起人（无需前缀）

**在 JSON 设计文件中**：用 `@@` 分隔
```json
"permissionFlag": "role:1@@role:2@@user:boss"
```

**在 API 请求中**：用数组
```json
"permissionFlag": ["role:1", "role:2", "user:boss"]
```

### 5.2 如何实现"部门负责人"审核？

方案一：**设计时配置角色**
- 将部门负责人赋予某个角色（如角色3），在节点配置 `permissionFlag: "role:3"`

方案二：**运行时动态指派**
- 启动流程时，业务代码查询申请人的部门负责人，作为 `permissionFlag` 传入：
```json
{
  "flowCode": "leave_apply",
  "businessId": "LEAVE-001",
  "permissionFlag": ["user:dept_manager_zhang"]
}
```

### 5.3 加签后，原办理人还能审批吗？

能。加签不会影响原办理人的任务。原办理人和加签人形成并行审批。

### 5.4 转办后，我还能看到这个任务吗？

不能。转办是彻底移交，任务从你的待办中消失，出现在目标办理人的待办中。但你可以在"我的已办"中看到转办记录。

### 5.5 委派后，被委派人批完，我还能操作吗？

能。被委派人审批完成后，任务会回到你的待办中。

### 5.6 驳回时能指定驳回到哪个节点吗？

能。传 `nodeCode` 参数即可：
```json
{
  "taskId": 555666777,
  "skipType": "REJECT",
  "nodeCode": "2",
  "message": "请重新填写"
}
```
如果不传 `nodeCode`，则按流程设计中 `REJECT` 连线自动跳转。

### 5.7 如何查询我发起的流程？

使用流程实例列表，按发起人筛选：

```
GET /flowIns/list?createBy={我的用户ID}
```

或者使用专门的"我的申请"接口：

```
GET /flowIns/myStarted
```

## 六、最佳实践

### 6.1 流程设计

1. **每个审批节点都要配置 REJECT 路径**，否则驳回会失败
2. **节点命名清晰**：用"组长审批"而非"节点3"
3. **合理使用角色而非具体用户**：`role:1` 比 `user:zhangsan` 更灵活
4. **使用监听器记录关键日志**：在开始、完成节点配置监听器

### 6.2 权限控制

1. **角色前缀约定**：统一使用 `role:N`（角色）和 `user:N`（用户）
2. **最小权限原则**：`system:flow:task:approve` 权限应只授予需要审批的人

### 6.3 加签/转办/委派的选择

| 你想做什么 | 用哪个 |
|-----------|--------|
| 让另一个人替我批，我就不管了 | 转办 |
| 我出差了，让小王代批，回来后我确认 | 委派 |
| 我觉得需要多一个人一起审批 | 加签 |
| 某个加签的人不需要批了 | 减签 |
| 这个流程不走了，结束掉 | 终止 |
| 我提交错了，想撤回重新填 | 撤销 |
